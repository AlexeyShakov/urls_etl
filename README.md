# urls_etl

Идея проекта

Я хочу реализовать на Go тренировочный pipeline-processing сервис, чтобы попрактиковаться в goroutines, channels, worker pool, fan-out/fan-in, rate limiting, backpressure и graceful shutdown.

MVP

В первой версии упрощаем задачу:

* есть один пользователь;
* список URL уже находится в памяти;
* pipeline запускается вручную, например через main или простой HTTP-запрос;
* не делаем Kafka, сложное хранилище очередей, несколько пользователей, pause/resume.

Что нужно реализовать:

1. Pipeline для обработки списка URL
Сервис получает список URL и запускает их обработку.

2.  Worker pool для запроса URL

Несколько worker-ов читают URL из channel, делают HTTP-запрос и получают результат.

3. Fan-out на 3 постоянных внешних сервиса

После получения результата по URL нужно отправить этот результат в 3 разных постоянных сервиса.

4. Worker-ы для внешних сервисов

Для каждого внешнего сервиса должны быть worker-ы, которые отправляют запросы и получают ответы.

5. Rate limiting

Нужно ограничивать скорость запросов к внешним сервисам. Изучить варианты:

* net/http настройки, например MaxConnsPerHost;
* token bucket / leaky bucket / liquid bucket подход.
* разница между concurrency limit и rate limit

6. Сохранение результатов

Результат ответа каждого из 3 сервисов нужно сохранить в БД.

7. Каналы и backpressure

Использовать bounded channels, чтобы не создавать миллион goroutine на миллион URL. Если БД или внешний сервис тормозит, pipeline должен естественно замедляться.

8. Контекст и остановка

Использовать context.Context, чтобы можно было корректно отменить выполнение pipeline.

Что изучить отдельно
* net/http.Transport
* MaxConnsPerHost
* MaxIdleConns
* MaxIdleConnsPerHost
* token bucket / leaky bucket / liquid bucket
* worker pool pattern
* fan-out / fan-in pattern
* graceful shutdown
* backpressure через bounded channels
* разница между concurrency limit и rate limit

Идеи для улучшения после MVP

1. Сохранять результат каждого этапа в БД

Не только финальный результат, а состояние каждого stage:

* URL получен;
* URL обработан;
* запрос в service A выполнен;
* запрос в service B выполнен;
* запрос в service C выполнен;
* результат сохранён;
* ошибка на конкретном этапе.

2. Трекинг прогресса pipeline

Нужно видеть, сколько задач находится на каждом этапе:

* сколько URL ожидают обработки;
* сколько сейчас обрабатываются;
* сколько успешно завершены;
* сколько упали с ошибкой;
* сколько задач находится на stage 1, stage 2, stage 3 и т.д.

3. Статистика

Собираем статистику по pipeline:

* общее количество URL;
* количество успешных;
* количество неуспешных;
* среднее время обработки;
* ошибки по внешним сервисам;
* количество retry;
* throughput.

4. Pause / Continue

Pipeline можно поставить на паузу и продолжить.

Важно: не нужно “замораживать goroutine”. Лучше сделать так:

* worker-ы перестают брать новые задачи;
* уже начатые задачи завершаются;
* состояние сохраняется в БД;
* при continue незавершённые задачи поднимаются из БД и снова отправляются в обработку.

5.Конфигурация worker-ов

Можно задавать начальное количество worker-ов:

* сколько worker-ов обрабатывают URL;
* сколько worker-ов ходят в service A;
* сколько worker-ов ходят в service B;
* сколько worker-ов ходят в service C;
* сколько worker-ов сохраняют результат в БД.

6. Динамическое добавление worker-ов

Во время выполнения pipeline можно увеличить количество worker-ов, чтобы ускорить обработку.

7. Retry policy

Добавить retry для временных ошибок:

timeout;
5xx от внешнего сервиса;
временная ошибка БД.

8. Resume после падения приложения

Так как состояние stages лежит в БД, после рестарта приложения можно продолжить pipeline с последнего незавершённого этапа.

Главная идея: goroutines выполняют работу, channels передают задачи между этапами, а БД хранит правду о состоянии pipeline.
